
# Xray Server Final

Self-hosted Xray server deployment for Ubuntu 24.04 using Docker Compose.

Проект предназначен для развёртывания сервера Xray с шестью вариантами подключения, автоматической генерацией конфигураций, ключей, TLS-сертификата и клиентских профилей для v2rayNG.

> Все секреты, ключи и готовые конфигурации генерируются непосредственно на сервере. Репозиторий содержит исходные файлы проекта и шаблоны, а не готовые секретные данные.

## Возможности

- Xray-core `26.6.27`.
- Docker Compose deployment.
- Шесть вариантов подключения.
- Пять пользователей с индивидуальными учётными данными.
- Генерация UUID, паролей, Short ID и REALITY key pair.
- Генерация самоподписанного TLS-сертификата с IP SAN.
- Использование TLS fingerprint для клиентской проверки сертификата.
- Выбор REALITY `dest` и `SNI` вручную или с помощью CSV RealiTLScanner.
- Автоматическая сборка конфигураций из шаблонов.
- Проверка конфигурации Xray перед запуском.
- Резервное копирование предыдущих конфигураций.
- Генерация готовых клиентских ссылок для v2rayNG.
- Отдельный Nginx для HTTPS XHTTP.
- Диагностический скрипт для проверки состояния компонентов.

## Архитектура

Проект состоит из двух Docker-контейнеров:

| Контейнер | Назначение |
|---|---|
| `xray` | Обработка подключений Xray и работа транспортов |
| `nginx` | Обработка HTTPS XHTTP подключений на порту 9443 |

Контейнеры взаимодействуют через отдельную Docker bridge network `proxy_net`.

Nginx подключается к Xray по внутренней сети Docker. Конфигурационные файлы и сертификаты подключаются к контейнерам через volumes.

### Схема

```text
                    Internet
                       |
                       |
              Public IP of server
                       |
       +---------------+----------------+
       |                                |
   Xray container                  Nginx container
       |                                |
   TCP / UDP ports                  TCP 9443
       |                                |
       +------------ proxy_net ----------+
```

## Состав репозитория

Репозиторий содержит исходные скрипты, шаблоны конфигураций и файлы, необходимые для развёртывания.

### Файлы в корне проекта

| Файл | Назначение |
|---|---|
| `deployment.sh` | Основной сценарий первичного развёртывания |
| `docker-compose.yaml` | Описание контейнеров, портов, volumes и сети Docker |
| `README.md` | Документация проекта |
| `.gitignore` | Исключение служебных, генерируемых и секретных файлов из Git |

### Каталог `scripts/`

| Файл | Назначение |
|---|---|
| `create-keys-and-cert.sh` | Генерация TLS-сертификата, REALITY ключей и пользовательских секретов |
| `select-reality-target.py` | Выбор REALITY `dest` и `SNI` вручную или из CSV RealiTLScanner |
| `build-configs.sh` | Подстановка значений в шаблоны, сборка конфигураций и проверка JSON |
| `generate-client-profiles.py` | Генерация клиентских ссылок для всех пользователей и протоколов |
| `checks.sh` | Диагностические проверки компонентов проекта |

### Каталог `xray/`

| Файл | Назначение |
|---|---|
| `config.json.template` | Шаблон конфигурации Xray |

Шаблон содержит структуру inbound, outbound, routing и параметры используемых протоколов. Секретные значения подставляются во время сборки конфигурации.

### Каталог `nginx/`

| Файл | Назначение |
|---|---|
| `nginx.conf.template` | Шаблон конфигурации Nginx |

Шаблон используется для создания рабочей конфигурации Nginx с параметрами проекта.

### Каталог `my-site/`

Предназначен для размещения собственных файлов сайта, если требуется использовать веб-содержимое через Nginx.

В исходном репозитории каталог может содержать только `.gitkeep`.

## Используемые порты

| Протокол | Транспорт | Порт |
|---|---|---:|
| VLESS REALITY Vision | TCP | 443 |
| Hysteria 2 | UDP | 443 |
| VLESS TLS + WebSocket | TCP | 8443 |
| Trojan gRPC REALITY | TCP | 8444 |
| VLESS XHTTP REALITY | TCP | 8445 |
| VLESS XHTTP TLS через Nginx | TCP | 9443 |

Все порты должны быть разрешены в сетевых правилах облачного провайдера, если они используются для входящих подключений.

Для UDP 443 необходимо отдельно убедиться, что UDP-трафик разрешён.

## Подготовка сервера

Перед развёртыванием необходимо:

1. Создать виртуальную машину с Ubuntu 24.04.
2. Убедиться, что назначен публичный IPv4-адрес.
3. Настроить правила сетевого доступа в облачной панели.
4. Разрешить SSH и используемые проектом порты.
5. Подключиться к серверу по SSH.

### Сетевые правила

| Порт | Протокол | Назначение |
|---|---|---|
| 22 | TCP | SSH |
| 443 | TCP | VLESS REALITY Vision |
| 443 | UDP | Hysteria 2 |
| 8443 | TCP | VLESS TLS + WebSocket |
| 8444 | TCP | Trojan gRPC REALITY |
| 8445 | TCP | VLESS XHTTP REALITY |
| 9443 | TCP | VLESS XHTTP TLS через Nginx |

Не открывайте порты, которые не используются или не нужны для выбранной конфигурации.

## Подготовка REALITY-цели

REALITY использует целевой сервер и SNI, которые задаются при формировании конфигурации.

В проекте предусмотрено два варианта выбора:

- Использовать значения по умолчанию.
- Выбрать собственную цель вручную или с помощью CSV RealiTLScanner.

При первичном развёртывании используются тестовые значения по умолчанию, если пользователь не задаёт другую цель.

### RealiTLScanner

RealiTLScanner используется для предварительного поиска и проверки кандидатов REALITY-целей.

Сканер запускается на локальном компьютере, а не на облачной серверной ВМ.

#### Подготовка сканера

1. Откройте официальный репозиторий RealiTLScanner:

   https://github.com/XTLS/RealiTLScanner

2. Перейдите в раздел Releases, если доступен готовый релиз для вашей ОС.

3. Скачайте подходящую сборку или соберите сканер согласно инструкции репозитория.

4. Запустите сканирование выбранных IP-адресов или диапазонов.

5. Для сканирования используйте подходящие параметры, включая проверку TCP 443 и TLS/SNI, в соответствии с инструкцией сканера.

6. Сохраните результаты в CSV ИЛИ воспользуйтесь командой ниже и выбререте в результате подходящий ВАМ ip и домен сайта.
```bash
./RealiTLScanner -addr "Ваш IP"
```

7. Перед использованием результатов убедитесь, что выбранная цель соответствует требованиям REALITY и доступна с вашего серверного IP.

Не используйте произвольные IP-адреса без предварительной проверки. Результаты сканирования не гарантируют постоянную доступность или пригодность цели.

#### Передача CSV на сервер

CSV создаётся на локальном компьютере. После сканирования передайте его на сервер по SSH/SCP или другим безопасным способом.

Не запускайте RealiTLScanner непосредственно на серверной ВМ проекта.

`Ниже представлена инструкция для CSV файла, но проще воспользоваться командой выше и подставить все вручную без пересборки проекта.`

### Выбор REALITY-цели из CSV

После передачи CSV на сервер выполните:

```bash
cd /opt/Xray-Nginx-Docker-server
sudo python3 scripts/select-reality-target.py /path/to/scanner.csv
```

Замените `/path/to/scanner.csv` на фактический путь к CSV.

Скрипт использует следующие поля:

- `IP` — IP-адрес выбранного кандидата.
- `CERT_DOMAIN` — домен сертификата, если поле заполнено.
- `ORIGIN` — альтернативный домен, если `CERT_DOMAIN` не заполнен.

При выборе SNI приоритет отдаётся `CERT_DOMAIN`, если он заполнен, иначе используется `ORIGIN`.

Wildcard-имена отклоняются.

Скрипт сохраняет выбранную пару `REALITY_DEST` и `REALITY_SNI` в `secrets/generated-values.env`.

После изменения REALITY-цели необходимо пересобрать конфигурации и перезапустить Xray:

```bash
cd /opt/Xray-Nginx-Docker-server
sudo bash scripts/build-configs.sh
sudo docker compose restart xray
```

Перед использованием новой цели рекомендуется проверить доступность выбранного IP и соответствие SNI.

## Первый запуск

Первичное развёртывание выполняется с помощью `deployment.sh`.

Из каталога проекта:

```bash
sudo bash deployment.sh
```

### Что делает deployment.sh

1. Проверяет наличие необходимых компонентов.
2. При необходимости устанавливает Docker.
3. Включает Docker в автозапуск.
4. Создаёт необходимые каталоги проекта.
5. Проверяет наличие секретов и TLS-сертификата.
6. При первичном запуске генерирует ключи, сертификат и учётные данные.
7. Предлагает выбрать REALITY-цель.
8. Собирает рабочие конфигурации из шаблонов.
9. Проверяет конфигурацию Xray.
10. Проверяет конфигурацию Nginx.
11. Запускает контейнеры Docker Compose.
12. Генерирует клиентские профили.
13. Настраивает права доступа к файлам и каталогам проекта.

Сценарий рассчитан на первичное развёртывание в `/opt/Xray-Nginx-Docker-server`.

Он не предназначен для повторной установки поверх существующего непустого каталога проекта.

При повторном запуске не следует удалять существующие секреты или сертификаты ради повторной генерации без резервной копии.

## Что создаётся при развёртывании

После успешного запуска появляется рабочая структура проекта.

### Каталог `secrets/`

Содержит:

- `generated-values.env` — переменные проекта, пользовательские секреты, параметры REALITY и TLS fingerprint.

Этот файл является конфиденциальным.

### Каталог `certs/`

Содержит:

- TLS-сертификат.
- Приватный TLS-ключ.

Сертификат самоподписанный и содержит IP SAN.

### Каталог `xray/`

После сборки появляется:

- `config.json` — рабочая конфигурация Xray.

### Каталог `nginx/`

После сборки появляется:

- `nginx.conf` — рабочая конфигурация Nginx.

### Каталог `output/`

Содержит:

- `client-profiles.txt` — готовые клиентские ссылки.

### Каталог `logs/`

Содержит журналы компонентов проекта:

- `logs/xray/`
- `logs/nginx/`

### Каталог резервных копий

При пересборке конфигураций предыдущие рабочие файлы сохраняются в резервных копиях с временной меткой.

Это позволяет восстановить прежнюю конфигурацию в случае неудачной сборки или изменения параметров.

## Клиентские профили

После успешного развёртывания генерируется файл:

```text
output/client-profiles.txt
```

В нём находятся профили для пяти пользователей.

Для каждого пользователя предусмотрено шесть протоколов:

1. VLESS TLS + WebSocket.
2. VLESS REALITY Vision.
3. VLESS XHTTP REALITY.
4. Trojan gRPC REALITY.
5. VLESS XHTTP TLS.
6. Hysteria 2.

Файл структурирован по пользователям и содержит параметры, необходимые для импорта профилей.

### Импорт в v2rayNG

1. Скопируйте нужную ссылку из `client-profiles.txt`.
2. Откройте v2rayNG на Android.
3. Импортируйте ссылку из буфера обмена.
4. Выберите добавленный профиль.
5. Подключитесь и проверьте работоспособность.

Не импортируйте все профили одновременно, если для тестирования достаточно одного.

Для первичной проверки рекомендуется импортировать один профиль и убедиться, что соединение работает, затем проверять остальные варианты.

### TLS fingerprint

Для TLS-профилей используется fingerprint сертификата.

Самоподписанный сертификат не означает, что клиенту необходимо отключать проверку сертификата через `allowInsecure`.

Вместо этого используется предусмотренная конфигурацией проверка fingerprint.

## Проверка работоспособности

После развёртывания рекомендуется выполнить диагностический скрипт.

```bash
cd /opt/Xray-Nginx-Docker-server
sudo bash scripts/checks.sh
```

Скрипт выполняет диагностические проверки компонентов проекта.

Он предназначен для проверки состояния и не должен использоваться как сценарий изменения конфигурации или перезапуска сервисов.

### Проверка Docker

```bash
sudo docker compose ps
```

### Проверка логов Xray

```bash
sudo docker logs xray
```

### Проверка логов Nginx

```bash
sudo docker logs nginx
```

### Проверка конфигурации Xray

```bash
cd /opt/Xray-Nginx-Docker-server
sudo docker compose exec xray xray run -test -config /etc/xray/config.json
```

Если контейнер не запущен, используйте тестовый запуск через Docker Compose или сначала проверьте состояние контейнеров.

## Безопасность

- Не коммитьте секреты в Git.
- Не публикуйте `secrets/`, приватные ключи, клиентские ссылки и готовые конфигурации.
- Не отправляйте `client-profiles.txt` в публичные чаты.
- Не публикуйте TLS private key.
- Не публикуйте REALITY private key.
- Не публикуйте пользовательские UUID, пароли и Short ID.
- Используйте SSH для администрирования.
- Ограничивайте доступ к серверу и его сетевым портам.
- Проверяйте права доступа к конфиденциальным файлам.
- Не удаляйте секреты без резервной копии.
- Не используйте публичные диапазоны сканирования без понимания объёма и допустимости сканирования.

### Права доступа

Проект предусматривает ограниченные права доступа к секретным файлам и генерируемым конфигурациям.

Файл с клиентскими профилями должен иметь права доступа `600`.

Секреты должны быть доступны только владельцу и не должны попадать в публичный Git-репозиторий.

### Docker

Xray-контейнер в текущей конфигурации запускается с `user: "0:0"`.

Это увеличивает последствия компрометации контейнера. Docker не является абсолютной границей безопасности.

## Примечания

- Проект не изменяет UFW, iptables/nftables или системную маршрутизацию автоматически.
- Настройка сетевых правил выполняется отдельно.
- Docker Compose используется для управления контейнерами.
- Секреты создаются непосредственно на сервере.
- TLS-сертификат самоподписанный.
- REALITY-цель может изменяться отдельно от TLS fingerprint.
- Клиентские профили генерируются на основе текущих секретов и параметров конфигурации.
- Для повторного развёртывания необходимо учитывать существующие сертификаты, конфигурации и секреты.
